# Rooms

Rooms are durable-until-closed, team-owned, realtime player snapshots. They are distinct from authentication sessions.

- A team administrator or content maintainer may create a room for that team. Guests and non-members cannot create rooms, and backend authorization is authoritative if membership changes while the create UI is open.
- Creation may be independent or source-backed. Independent rooms have no song, collection, or setlist metadata and start with an empty content snapshot; source-backed rooms capture only chord-song items from the selected song, collection, or setlist without retaining source metadata. Blob-only songs and media slots are omitted, and retained songs have their blob references stripped. Both use the default musical state and open the creator in Sheet mode.
- Rooms created from a setlist also seed the separate next-song queue with unique chord-song snapshots in setlist order. The chord-only setlist snapshot remains immutable; promoting a seeded queue item selects its captured content item rather than duplicating it.
- Source-backed creation requires read access to the selected source and write access to the separately selected owning team. The source is resolved server-side, copied into the room at creation time, and later source edits do not change the captured content. Source and destination teams may differ.
- A creator may provide a room name of up to 80 characters; blank or omitted names receive a generated worship-themed verb/noun name. The backend persists one exact host session link for realtime authority and retains the linked user account for the HTTP room-list and close contract. Session IDs remain connection-scoped authority for realtime commands.
- A room's captured base content is immutable. Queue promotion is the explicit content-management operation: it appends an immutable song snapshot; source edits, likes, layout, scrolling, and other local preferences never mutate captured room content.
- The exact host session is the only realtime room host. Host authority survives device disconnects and session lease expiry; a valid resume credential restores that same host session. A different session for the same user is not the host. When content is present, the host controls item, effective language, and transposition; each session keeps a fixed Sheet, AV, or Slide connection role.
- At most one session owns AV authority. AV controls only the structured projection payload; Slide sessions are passive. Another session may claim AV after the previous AV session's lease expires.
- Sheet sessions choose a Chords or Text view when joining. Text hides chord symbols locally; the choice is stored on the session record as `hide_chords`.
- Every join without a valid resume credential creates an independent session, including when the authenticated user already has another session in the room. Authenticated profile data is resolved through `user_id`; only anonymous sessions store `guest_display_name`.
- Invite and resume credentials are high-entropy room-scoped secrets. The durable invite is stored only as a hash and becomes invalid when the room closes.
- WebSocket clients receive a complete snapshot before ordered field deltas. Desired-state command retries are idempotent, and revision gaps require one new snapshot.
- Active room clients heartbeat every 10 seconds. Session leases survive a brief disconnect for 30 seconds and independently determine presence and AV occupancy; a room remains open until an authorized user explicitly closes it.
- The host, a current team administrator, or a current content maintainer may close the room. Close authorization is evaluated from the current authenticated account and team role on every request; guests, unrelated users, and anonymous sessions cannot close it. Closing atomically deletes the room, its captured snapshot, and all session records; it does not persist a closed marker.
- Anonymous credentials can read only the captured chord-song room state. They never authorize normal library endpoints.
- New rooms disable unauthenticated guest access by default; existing rooms retain their setting. The host can enable or disable guest access at any time. While disabled, invite inspect/join rejects new anonymous sessions; existing guest resume credentials still reconnect. This setting is persisted as `guest_access_allowed`.
- The host can lock a room at any time. While locked, new authenticated and anonymous joins are rejected; existing session resume credentials still reconnect. Unlocking allows new joins again without changing the room contents or session roles. This setting is persisted as `new_joins_locked`.
- The host controls whether authenticated members may add songs from their normal library with the persisted `queue_additions_allowed` flag. Existing rooms retain their setting; new rooms default to `queue_additions_allowed: false`. Changing this setting is revisioned and broadcast as `queue_access_updated`.
- When `queue_additions_allowed` is true, authenticated sessions may add songs available through their normal library access. When it is false, new library additions are rejected, but all existing queue entries remain usable. Setlist-backed rooms still seed unique song snapshots into the queue at creation, and setlist media slots are ignored.
- Authenticated sessions browse the current queue in queue order, alphabetical order, or their own liked-song view. A liked-song query is authenticated and room-scoped because personal likes are never included in the shared room snapshot. Anonymous guests may view, order, and vote on the current queue but do not have a personal Liked view.
- Queue additions are append-ordered and never change the current item automatically. New and setlist-seeded queue items start unplayed, and a newly created room has no active queue item even though its player view is positioned at the first content item. Every session, including anonymous invite guests, may toggle at most one upvote per queued item. Queue order is server-ranked with all unplayed items first, descending upvotes within that section, then played items with stable existing-order ties. Only the durable room host may activate or remove queue entries; activating the top item is the room's next-song action, while any queue item may be activated directly. The first activation makes the selected song current without marking the default first item played; later activation makes the selected song current, marks the previously active queued song played and clears its votes, removes the selected item's old votes, and appends a fresh zero-vote unplayed copy of the selected song to the queue. Selecting the current song itself does not mark it played. Upvoting a played item marks it unplayed before ranking; removing that upvote does not mark it played again. A song ID is rejected only while that song is already queued; songs that have already been shown can be queued again. Anonymous invite guests may vote and view the queue but may not add songs or manage it.
- Setlist-seeded entries remain unplayed until explicitly activated, and queue records created before the played field existed deserialize as unplayed.
- Session expiry is event/request-driven; the backend does not scan or persist rooms on a schedule. The rollout migration converts historical participants into sessions, preserves resume credentials, and invalidates old short-lived tickets. Deployments must drain active room WebSockets before applying it; clients reconnect with their preserved resume credentials and receive fresh tickets.
- Socket fan-out is immediate within one process. Across backend instances, clients converge from authoritative database state on the next active-room heartbeat; shared pub/sub is needed only to remove that bounded delay.

## Realtime messages

The WebSocket at `/api/v1/rooms/ws` accepts the connection ticket in the first JSON message, never in the URL.

Client message types are `authenticate`, `heartbeat`, `update_musical_state`, `update_projection`, `update_guests_allowed`, `update_room_locked`, `request_snapshot`, and `leave`. Mutation messages carry a unique `command_id`.

Server message types are `snapshot`, `heartbeat`, `musical_state_updated`, `projection_updated`, `guests_allowed_updated`, `room_locked_updated`, `queue_access_updated`, `sessions_changed`, `queue_updated`, `command_accepted`, `command_rejected`, and `room_ended`. Snapshots and deltas carry the current monotonically increasing room revision; queue updates replace the complete queue for that revision.

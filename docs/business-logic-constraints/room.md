# Rooms

A Room is a durable, team-owned snapshot of songs with an append-only shared message history. It is separate from authentication sessions and cannot be edited after creation.

- A user with write access to a team can create or delete that team's Rooms. Creation captures the selected song, collection or setlist content on the server. Later source edits do not change the Room. Non-song media and blob-only slots are not captured; every captured song entry stays in the room's table of contents for its lifetime.
- Any signed-in user with a direct room link can join, even if they do not belong to the owning team. Anonymous users cannot join. Join and replay require authentication; the one-use connection ticket is sent as the first WebSocket message, and the resume credential is sent in the `x-room-resume` header.
- Each join without a valid resume credential creates a new visit identity. Reconnecting with the account- and room-bound resume credential keeps that identity. A visit can vote independently of other visits from the same account. Votes remain in history after the visit goes offline.
- Room replay includes the durable room creation time. Live presence entries include the time the visit first became online; that time stays stable across concurrent sockets and the 30-second disconnect grace period, but is process-local and is not a historical visit record.
- There is no privileged host for navigation, in-room close control, anonymous guest mode, mutable song pool, or separately editable queue. All connected participants can activate songs, navigate AV slides, and vote; AV-mode clients publish the rendering configuration followed by slide-only clients. Room deletion is performed from the room list by a team editor.
- Shared state starts with no selection, explicit background change, AV rendering configuration, votes or played songs. AV rooms show the built-in default background until one is set. An AV-mode client publishes the current AV configuration on join and after each change; slide-only clients use it for line layout, bilingual output, language selection, whitespace, transitions, and live/blank/blackout state instead of their local AV settings. Before the first configuration message, slide-only clients use built-in defaults. The room's fixed song entries are ranked by unplayed first, descending visit vote count, then original source order. Every entry appears once in the virtual queue; no message can add or remove a song.
- An activation sets the selected song, source section and AV slide, marks that entry played and clears its votes. Activating the same song again has the same effect. Sheet navigation sends the selected section with slide zero; AV navigation also sends the rendered slide index so participants can follow moves within a section. A slide-selection message leaves votes and played state unchanged. Legacy selections without a section replay at the corresponding section boundary. A vote message sets one visit's vote to an absolute true or false value. Setting it true marks a played song unplayed; clearing a vote does not mark it played again.
- AV participants can replace the shared background with a preset or custom image or video reference. The latest `set_background` message is part of replay, so joiners and reconnecting clients receive it. Custom media still uses each recipient's normal media access; the preset is rendered if the asset cannot be fetched. `set_av_configuration` carries AV rendering preferences separately from the background and is replayed to room members.
- Team membership is checked at create, list and delete time. Room-link access is checked against the signed-in user and the resume credential. Credentials are not placed in URLs and are never included in local diagnostics.
- The storage model is `room` (owner, name, immutable captured content), `room_change` (ordered message records), `room_message_epoch` and `room_visit` (account-bound resume and one-use ticket hashes). Appending history is idempotent for the same room, ID and full envelope. Message history is ordered by `(epoch, sequence)` and may have gaps.

## Realtime and replay limits

- One backend replica is required. Ordering, current presence, broadcasts and live duplicate IDs are process-local; cross-replica pub/sub is not implemented.
- The persistence queue has a capacity of 256 changes. It retries a failed queued append up to three times. If the queue is full, or retries fail, a change is still broadcast but is not saved. Later changes can be saved, so history may contain gaps.
- A REST history read waits up to eight seconds for writes already queued through the captured boundary. A successful response may omit a live change whose persistence was dropped. The server does not repair incomplete history from its in-memory state and does not warn the user about gaps. A later absolute message repairs only the state it explicitly sets; a lost final message can leave replay stale.
- A join establishes the WebSocket first, captures a boundary and buffers up to 256 live changes while the client fetches history. The client replays available history, then drains messages after the boundary without a race. Presence is the current online list, not replay history. Disconnected visits have a 30-second grace period.
- Live message IDs are remembered in a bounded 4,096-ID active-room cache. Clients send UUIDs and do not retry messages. Reused IDs are not guaranteed to be deduplicated after that cache is evicted or a process restarts. Persistence itself checks exact duplicate envelopes.
- Client diagnostics are local and opt-in. The shared replay/live log is limited to 1,000 entries or 512 KB, resets for each room player session, includes a truncation marker and excludes room credentials. It is not a durable or complete export.

## Migration and rollout

The forward migration is intentionally destructive. Back up the database and stop/drain old room WebSockets before release; old rooms, room sessions and their snapshots are discarded. There is no mixed-version client compatibility or automatic data conversion. New room links use `/rooms/{room_id}` and require a signed-in account. Do not run the migration against a deployed database as part of development or verification.

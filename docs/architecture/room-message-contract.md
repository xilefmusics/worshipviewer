# Room message contract

Rooms hold a fixed, source-ordered snapshot of chord songs. The room-scoped zero-based `song` index distinguishes captured entries even when their library song IDs match. A zero-based `section` index refers to a source section; the zero-based `slide` index refers to a rendered AV slide in that song. The server validates the song and section against its cached room content, and checks that background presets and optional media references are structurally valid. AV slide indices are client-rendered, so a receiver uses the index when it exists in its local slide list and falls back to the section boundary when it does not. Initial replay state has no selection, explicit background change, AV configuration, played songs or votes; AV rooms show the built-in default background until someone sets one. AV backgrounds are shared separately. The AV controller publishes a rendering configuration when it joins and whenever it changes. Slide-only members use it for line splitting and layout, bilingual rendering, per-song language, whitespace handling, transitions, and live/blank/blackout state; before the first configuration they use built-in defaults. Sheet layout and chord visibility remain local.

Each persisted change contains a unique client message ID, room ID, authenticated visit ID, server order and an absolute payload. The server derives visit identity from the one-use connection ticket; clients cannot set it. A new visit creates a fresh identity. A resume credential bound to both the account and room retains the identity for automatic socket reconnects. REST replay uses `x-room-resume`; the secret is never included in URLs or the message log.

```json
{"type":"selection","song":1,"section":2,"slide":7,"activate":false}
{"type":"vote","song":1,"voted":true}
{"type":"set_background","background":{"preset":2,"image":{"media_id":"media:123","asset_id":"asset:456"}}}
{"type":"set_av_configuration","configuration":{"content_layer":{"max_lines_per_slide":4,"balance_slide_lines":true,"font_size":60,"text_align":"center","vertical_align":"center","horizontal_align":"center","text_shadow":"none","text_transform":"uppercase","primary_text_lightness":100,"secondary_text_lightness":65},"transition":{"style":"none","duration_ms":0},"bilingual_enabled":true,"collapse_lyric_whitespace":true,"language_by_item":{"1":1},"screen_state":"live"}}
```

- `selection` replaces the song, source section and AV slide. `activate: true` marks that fixed entry played and clears all votes. Selecting any song is an activation; moving between sections or slides is not. Sheet navigation sends the selected section and slide zero; AV navigation sends both the source section and the exact rendered slide index. Legacy messages have no `section`; replay treats their previous `slide` value as a section and starts at that section boundary.
- `vote` sets this visit's vote. Setting it to true also marks the song unplayed; setting it to false removes the vote without changing played state. Votes remain after the visit disconnects.
- `set_background` replaces the shared AV background preset and optional custom image reference. It is replayed for joiners and reconnects. A custom image is fetched using each participant's normal media access; if unavailable, the preset remains visible as a fallback.
- `set_av_configuration` replaces the AV rendering snapshot. AV-mode clients publish it; its latest value is replayed to slide-only joiners and reconnects. The server validates setting ranges and song indexes. Language overrides that are unavailable in a recipient's song fall back to that song's default language.
- The virtual queue contains each captured entry once. Rank unplayed entries first, then descending vote count, then original source index. It is derived from replay and is never separately persisted.

Order is `(epoch, sequence)`, compared lexicographically. A backend process durably reserves a new epoch before accepting changes to a room; its sequence begins at one. A single backend replica is required because live fan-out and current presence are process-local. Sequence gaps are expected when the bounded persistence queue is full. A restarted process uses a new epoch rather than guessing the last accepted sequence from incomplete history.

The client generates UUID message IDs and does not retry a send. Exact retries among the server's 4,096 most recent IDs in an active room are ignored; conflicting reuse in that window is rejected. The database append is idempotent for an exact room/ID/envelope retry. Live IDs are held in bounded memory and are cleared when an active room is evicted or the process restarts; clients must not reuse IDs. These choices keep live acceptance off the database path.

Accepted changes are broadcast to every socket, including the sender, before persistence. A 256-entry persistence queue retries each stored change up to three times; if the queue is full or retries fail, the message stays live and is absent from history. Later messages can still be stored. A successful history request can therefore omit messages, and no snapshot repairs those gaps. Later absolute selections, votes, background and AV configuration messages repair only the state they explicitly set; a lost final message can leave replay stale.

Joiners establish a ticket-authorized socket before requesting REST history. The socket captures an ordered boundary and buffers subsequent changes (up to 256) while REST returns the immutable room, its durable `created_at` time and saved history through that boundary. The client applies history, signals `history_ready`, then applies buffered changes after the boundary in server order. Messages at or before the boundary are excluded from the buffer, so the replay boundary is applied once. Presence is sent separately and is never replayed from history. Each online presence entry includes `joined_at`, the time that visit first connected in the current process; concurrent sockets and reconnects during the grace period retain it. A history request waits up to eight seconds for writes already queued through its boundary; deliberately dropped messages do not block it.

Presence is current process state. A disconnected visit stays online for a 30-second grace period; concurrent sockets for the same visit appear once. A room supports at most 500 visits, 1,000 sockets and four sockets per visit. WebSocket event buffers hold 128 messages, the handoff buffer holds 256, incoming text is limited to 32 KB, and a client is disconnected after a broadcast lag or a missed 60-second pong deadline. WebSocket tickets expire after two minutes and are consumed once.

Room creation and deletion require team write access. Any signed-in user who has the room link can join; anonymous users cannot. Existing room clients must be drained before the destructive forward migration. Back up the database first; the migration deletes old `room` and `room_session` rows and creates the replacement tables. This change has no deployed-data rollback path.

The opt-in client diagnostics viewer and JSON download show the same per-player session log. It includes replay/live source and server order, may be incomplete or contain duplicates, and is bounded to 1,000 entries or 512 KB. It contains no resume credential or connection ticket and is not a database export.

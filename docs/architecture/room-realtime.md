# Room realtime architecture

HTTP performs discovery, creation, invitation exchange, role claims, reconnect-ticket exchange, explicit closing, song-pool updates, room-scoped pool-song search, and scoped media reads. A server-authoritative WebSocket carries presence and shared-state commands.

SurrealDB is authoritative for room state; process memory contains active socket broadcasters only. The base content snapshot is captured at room creation, while pool-prefilled and promoted queue songs are appended as immutable snapshots. Queue state, per-participant vote state, and other mutable fields update together with the room revision. A room's `closed_at` field is its only lifetime flag. Heartbeats update participant presence leases; they never end a room. Commands are checked against the room-local participant represented by their one-use connection ticket, and host commands compare that participant's authenticated `user_id` with the durable room host account. The persisted song pool is independent of captured source metadata: selecting a pool snapshots currently available songs into the queue, while the separate `open` flag controls future normal-library additions. Restricted pool resolution is checked before the pool and queue update, so unavailable sources produce no mutation. Setlist media slots are excluded. After snapshotting, the room's scoped media authorization serves captured content to every participant; anonymous invite participants remain view-only for song additions but may vote on queue entries. The room host and AV host therefore remain separate even when both participants use the same account.

The client renders a complete snapshot before accepting incremental state. It tracks the latest revision, ignores older data, and requests a fresh snapshot after a gap. Reconnect uses a participant resume credential with bounded exponential backoff. Existing non-room AV output continues using the browser-local `BroadcastChannel` path.

Source-backed rooms hydrate their initial immutable snapshot from the selected readable library item at creation time. Independent rooms retain the empty snapshot behavior. Setlist-backed rooms additionally seed the next-song queue with unique song snapshots in source order; promotion reuses the matching captured content item. Scoped media authorization resolves each captured blob against its actual owning team, allowing the room team and source team to differ.

There are no scheduled backend room jobs. Participant expiry is evaluated by the request or socket event that touches a room; room closure is explicit and online-only. Same-instance sockets receive deltas immediately through the process-local broadcaster. With multiple Cloud Run instances, SurrealDB remains the shared authority and a socket on another instance detects a revision change on its next active-room heartbeat and requests one fresh snapshot. Shared pub/sub or a database change feed remains an optional latency improvement for immediate cross-instance fan-out.

Queue additions, participant votes, host removal, promotion, and song-pool changes use the room revision for optimistic concurrency. Additions and vote changes publish a `queue_updated` delta; pool-only access changes publish a `song_pool_updated` delta. Pool selection that appends queue entries publishes a complete snapshot because it changes both pool and queue state. Promotion publishes a complete snapshot because it changes both queue state and player content/current item. A pool change never removes or reorders existing queue entries.

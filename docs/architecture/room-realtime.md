# Room realtime architecture

HTTP performs discovery, creation, invitation exchange, role claims, reconnect-ticket exchange, explicit closing, and per-user queue-like reads. A server-authoritative WebSocket carries presence and shared-state commands, including queue-access and room-lock updates.

SurrealDB is authoritative for room state; process memory contains active socket broadcasters only. Room content is captured once and stored inline in `player_room.content_json`. It contains only chord-song items; blob-only songs and setlist media slots are omitted, and retained songs have their blob references stripped. `queue_json` stores only song IDs and mutable queue metadata; queue consumers resolve each ID against the first matching content item. Queue state, per-session vote state, and other mutable fields update together with the room revision. Closing a room atomically deletes its room and session records; `closed_at` is retained only for compatibility with older persisted rows. Heartbeats update session presence leases; they never end a room. Commands carry the authenticated session context established by the connection ticket. Host commands compare that exact session ID with `host_session_id`; another session belonging to the same user is not host. The persisted `queue_additions_allowed` flag controls future normal-library additions; disabling it leaves every existing queue entry intact. The persisted `new_joins_locked` flag prevents new authenticated or anonymous joins while allowing existing session resume credentials to reconnect. The persisted `guest_access_allowed` flag controls anonymous invite access. Anonymous invite sessions remain view-only for song additions but may vote on queue entries. The room host and AV host therefore remain separate even when both sessions use the same account.

The client renders a complete snapshot before accepting incremental state. It tracks the latest revision, ignores older data, and requests a fresh snapshot after a gap. Reconnect uses a session resume credential with bounded exponential backoff; a reconnect rotates the ticket and connection generation without creating another session. Existing non-room AV output continues using the browser-local `BroadcastChannel` path.

Source-backed rooms hydrate their initial immutable chord-song content from the selected readable library item at creation time, without persisting source metadata. Independent rooms retain the empty content behavior. Setlist-backed rooms additionally seed the next-song queue with unique song-ID references in source order; promotion resolves the matching captured content item. Mixed sources are filtered to the chord songs that can be represented by the room contract.

There are no scheduled backend room jobs. Session expiry is evaluated by the request or socket event that touches a room; room closure is explicit and online-only. Same-instance sockets receive deltas immediately through the process-local broadcaster. With multiple Cloud Run instances, SurrealDB remains the shared authority and a socket on another instance detects a revision change on its next active-room heartbeat and requests one fresh snapshot. Shared pub/sub or a database change feed remains an optional latency improvement for immediate cross-instance fan-out.

Queue additions, session votes, host removal, promotion, queue-access changes, and room-lock changes use the room revision for optimistic concurrency. Queue item playback state is persisted alongside the queue JSON, while session votes remain in the separate vote map. An addition that introduces a song appends one normalized content item and publishes `content_item_added` with that item, its TOC row, and the lightweight queue; an addition that reuses existing content publishes `queue_updated`. Vote, removal, and ordering changes publish `queue_updated`; queue-access changes publish `queue_access_updated`; room-lock changes publish `room_locked_updated`. Promotion resolves the referenced content item, updates musical state and queue metadata, and publishes `playback_updated` with only those fields. Upvoting a played item changes it back to unplayed before the server re-ranks the queue; unvoting does not change that state. Queue payloads are ranked with unplayed items first and stable ties within each playback section, so no new realtime message is needed. Personal queue likes are fetched through the authenticated `GET /api/v1/rooms/{id}/queue/likes` endpoint rather than broadcast in shared snapshots.
